- (decision) [ADOPTED] Stack app : React/Next.js, hébergement Netlify, stockage 100% local storage, pas de backend/DB, PWA mobile-first (source: addendum.md)
- (decision) [ADOPTED] UI framework : shadcn/ui comme squelette sobre, couche de marque Crounch par-dessus (source: DESIGN.md)
- (constraint) Catalogue = JSON hébergé sur GitHub, refetch à chaque ouverture (pas figé au build) ; État de dégustation = local storage par appareil, jamais transmis (source: prd.md FR-1..FR-4)
- (question) Ouvert (PRD §8) : mécanisme de service du JSON (raw.githubusercontent.com / GitHub Pages / jsDelivr) ; source de vérité scraping Brets vs Open Food Facts ; mode dégradé si aucun cache local
- (decision) Monorepo unique : l'app Next.js et l'outil de scraping vivent dans le même repo (scraper dans un dossier scripts/ ou tools/), pas de repo séparé
- (decision) JSON catalogue servi via raw.githubusercontent.com, committé directement dans le repo par le scraper (résout PRD §8 Q2) — implique un cache CDN GitHub de quelques minutes, acceptable pour ce cas d'usage
- (decision) Source de vérité scraping : brets.fr prioritaire en cas de divergence (données éditeur/visuels officiels) ; Open Food Facts en complément/fallback (résout PRD §8 Q1)
- (decision) Premier lancement hors-ligne sans cache : état d'erreur explicite ("Impossible de charger le catalogue, vérifie ta connexion") + bouton réessayer, jamais un catalogue vide silencieux (résout PRD §8 Q3)
- (decision) Stratégie de chargement du catalogue : stale-while-revalidate — afficher immédiatement le cache local si présent, puis rafraîchir en fond dès réponse réseau ; en absence de cache, attendre le fetch (avec état d'erreur si échec, cf. décision précédente)
- (decision) Next.js en export statique (output: export) — aucun code serveur, tout le comportement (fetch catalogue, local storage) est côté client ; déploiement Netlify comme site statique
- (version) Next.js 16.x (stable, App Router, output: export vérifié compatible mi-2026) ; shadcn/ui compatible export statique sans configuration spéciale
- (decision) PWA/service worker : Serwist (successeur maintenu de next-pwa, standard 2026 pour Next.js + export statique) pour le manifest + precaching de l'app shell
- (decision) [ADOPTED] Frontière de données : le cache du Catalogue (remote, rejouable, clé par ID de Saveur stable) et l'État de dégustation (local storage, autoritatif, clé par ID de Saveur) sont deux stores indépendants qui ne se fusionnent jamais par index/position — seule la jointure par ID est permise, pour que le rafraîchissement du Catalogue ne puisse jamais écraser ou désynchroniser l'État de dégustation
- (decision) Outil de scraping en Node.js/TypeScript, même écosystème/toolchain que l'app (un seul langage dans le repo), CLI exécuté manuellement par le mainteneur, vit dans scripts/ ou tools/
- (event) Reviewer Gate lancé : lint_spine.py (0 finding) + reviewer versions/factuel + reviewer adversarial (2 subagents parallèles)
- (decision) Reviewer versions : bug trouvé — catalogue.json placé dans public/ serait figé au build par Next.js export statique, contredisant FR-1/UJ-3 (mise à jour du catalogue SANS redéployer l'app). Fix : catalogue.json vit hors de public/ (ex: data/ à la racine du repo), commité par le scraper, fetché au runtime via raw.githubusercontent.com — jamais bundlé par le build Next.js
- (decision) Reviewer versions : rate limit raw.githubusercontent.com non-authentifié resserré à ~60 req/h/IP depuis mai 2025 — accepté comme risque faible pour cet usage (1 fetch par ouverture d'app, faible nombre d'utilisateurs), atténué par le cache local (stale-while-revalidate)
- (decision) Reviewer versions : Serwist + output:export a un piège connu de génération de sw.js (issue vercel/next.js#73457) — noté en Deferred comme point d'attention à l'implémentation, pas un blocage architectural
- (decision) Reviewer adversarial : plusieurs trous bloquants trouvés dans AD-1/AD-2/AD-4/AD-5 — absence de schéma partagé Catalogue/État de dégustation, dérivation d'ID instable, clé de matching de scraping non définie, pas de garde anti-race sur le rafraîchissement réseau, conflit possible entre cache Serwist et fraîcheur du catalogue, pas de frontière Client Component explicite. Tous corrigés par extension des AD existants + nouveaux AD-7 (schéma partagé versionné) et AD-8 (mutation atomique de l'État de dégustation)
