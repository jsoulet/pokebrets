- (note) Input structuré et pré-trié : prd.md (final) + addendum.md, DESIGN.md/EXPERIENCE.md (UX finalisée), ARCHITECTURE-SPINE.md (architecture finalisée le 2026-07-30) — les 3 documents PRD open questions ont déjà été résolues par l'architecture (AD-2, AD-3, AD-5)
- (decision) Why : vision à réaliser — Johan (et ses potes) veulent savoir en un coup d'œil quelles saveurs de chips Brets ils ont déjà goûtées, sous forme de petit carnet de collection ludique (façon pokédex), projet perso/hobby sans ambition de produit public
- (capability) CAP-1 intent: le système peut charger le Catalogue à jour depuis un JSON hébergé sur GitHub à chaque ouverture de l'app ; success: une requête réseau est déclenchée à chaque ouverture, avec repli sur le cache local si elle échoue, ou état d'erreur explicite si aucun cache n'existe (source: PRD FR-1)
- (capability) CAP-2 intent: l'utilisateur peut visualiser tout le Catalogue sous forme de grille visuelle façon bingo/pokédex, saveurs archivées visuellement distinguables ; success: chaque Saveur apparaît comme case distincte, l'archivage est visible sans suppression de la grille (source: PRD FR-2)
- (capability) CAP-3 intent: l'utilisateur peut marquer une Saveur comme goûtée ou revenir en arrière ; success: le clic bascule l'État de dégustation immédiatement, écrit en stockage local sans action de sauvegarde explicite (source: PRD FR-3)
- (capability) CAP-4 intent: le système peut restaurer l'État de dégustation de l'utilisateur à chaque réouverture, sur le même appareil ; success: après fermeture/réouverture, toutes les Saveurs cochées restent cochées, jamais transmises à un serveur ni partagées entre appareils (source: PRD FR-4)
- (capability) CAP-5 intent: le mainteneur peut lancer un outil qui scrape les données de saveurs (brets.fr / Open Food Facts) et régénère le JSON du Catalogue sans redéployer l'app ; success: l'outil produit un JSON conforme au schéma, ré-exécutable pour intégrer de nouvelles saveurs sans intervention manuelle sur les entrées existantes (source: PRD FR-5)
- (constraint) Aucun compte, aucun backend, aucune base de données — 100% client, État de dégustation en local storage par appareil uniquement, jamais transmis (source: PRD Non-Goals, addendum.md)
- (constraint) Le Catalogue doit rester actualisable par le mainteneur sans reconstruire/redéployer l'app (JSON hors du bundle Next.js, refetch à chaque ouverture) (source: PRD FR-1, UJ-3, ARCHITECTURE-SPINE.md AD-2)
- (constraint) L'app doit rester rapide et légère en usage mobile — cas d'usage principal en rayon de supermarché — ne pas sacrifier la vitesse de chargement à l'exhaustivité des métadonnées (source: PRD SM-C1)
- (non-goal) Pas de compte utilisateur, pas de partage social/comparaison entre utilisateurs, pas de scan de code-barre, pas d'ajout manuel de saveur par l'utilisateur final, pas de synchronisation multi-appareils, pas de vocation à devenir un produit public ou monétisé, pas d'ambition de scalabilité (source: PRD §5)
- (decision) Success signal : Johan et ses potes utilisent réellement l'app en rayon ou après avoir goûté une chips, sans l'abandonner après quelques semaines (source: PRD SM-1)
