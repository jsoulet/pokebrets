## What Went Well

- **Architecture held up under pressure.** Every architectural decision (AD-2 remote Catalogue exclusion, AD-4 no server code / static export, AD-7/AD-8 shared schema) survived all 9 stories without a single workaround or violation discovered in review. The upfront architecture spec (Story 1.2's Zod schema, Story 1.3's cache/network design) paid off directly.
- **The adversarial 3-reviewer code-review process caught real, high-value bugs consistently**, not just style nits:
  - Story 1.5: stale-closure bug in `toggleTasted()` — rapid double-toggle could get stuck never returning to "not tasted". Found independently by all 3 reviewers.
  - Story 1.7: `isOffline` never reset to `false` after a successful-but-ignored (stale) revalidation.
  - Story 1.8: manifest double-precache (empirically confirmed via `grep -c` on `sw.js`) + a revision-fallback bug that could never trigger (`?? crypto.randomUUID()` on an empty string, not null).
  - Story 1.3: no fetch timeout, no unmount guard, string-comparison bug on `generatedAt` freshness.
- **Empirical verification became a habit, not an afterthought.** Several of the most important findings (Story 1.8's precache duplication, the `spawnSync` fallback bug, Story 1.5's stale-closure) were verified with direct reproduction (grep counts, isolated `spawnSync` tests, targeted unit tests) before being accepted — this avoided fixing phantom bugs and built confidence in what shipped.
- **Story 1.9's mid-review scope change (dropping Open Food Facts entirely) was handled cleanly** — a "Decision" finding escalated to the user, a real architecture simplification followed (fewer sources, fewer failure modes), not just a patch band-aid.
- **Consistent triage discipline**: every code review dismissed a comparable number of noise findings (false positives from diff construction, YAGNI concerns, spec-conformant "issues") with documented rationale, keeping the signal-to-noise ratio high across 9 rounds.

## Challenges / Friction Points

- **Diff construction caused recurring false positives.** In Story 1.4 and Story 1.8, excluding large/binary files (lockfile, PNG icons) from the diff sent to review subagents caused reviewers to flag them as "missing" when they were genuinely committed. This happened twice — a preventable pattern once identified.
- **Build-order pitfalls tied to Next.js 16 + static export appeared twice** in different forms: Story 1.3's cache/hook timing issues, and Story 1.8's genuinely tricky `next build` (copies `public/`→`out/`) vs `serwist build` (writes `sw.js` after) ordering bug — a real, documented upstream issue (vercel/next.js#73457), not a coding mistake, but it cost real debugging effort to isolate.
- **Stale-state/closure bugs were the single most recurring class of finding**, showing up in Stories 1.3 (unmount races), 1.5 (toggle closure), 1.7 (isOffline not reset), and flagged again as a deferred architectural gap (`revalidate()` request-ordering, no `requestId`/`AbortController`) that has been present since Story 1.3 and was never fully resolved — only patched around at the edges each time it resurfaced.
- **Accessibility (focus management, aria-labels, tap targets) issues were found in nearly every UI story** (1.4, 1.5, 1.6, 1.7) — never blocking, always patched, but indicates these weren't being verified proactively pre-review; the adversarial review acted as the actual safety net rather than a confirmation step.

## Key Patterns Across All 9 Stories

1. **Recurring bug class: stale/async state handling** (4 stories affected — 1.3, 1.5, 1.7, plus the still-deferred `revalidate()` ordering gap). This is the strongest signal for anything resembling "process improvement": state derived from React closures or unordered async responses needs a default posture of suspicion during dev, not just during review.
2. **Recurring bug class: accessibility on interactive elements** (4 stories — 1.4, 1.5, 1.6, 1.7): aria-labels, tap target sizing, focus traps/returns. All caught and fixed, none shipped broken, but always caught in review rather than in initial implementation.
3. **Diff-construction false positives** (2 stories — 1.4, 1.8): worth pre-empting explicitly in future review setups (e.g., a one-line note to reviewers when excluding lockfiles/binaries from a diff).
4. **One unresolved deferred architectural gap surfaced 3 times in different guises**: no request-ordering/AbortController in `lib/catalogue/index.ts`'s `revalidate()`. First seen in Story 1.3 (deferred), touched again in Story 1.7 (deferred again, same root cause), never actually fixed. This is the epic's single most consistent piece of carried-forward technical debt.
